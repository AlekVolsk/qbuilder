# План: форматирование значений, экранирование, LIKE, upsert

Статус: на утверждении. До утверждения код не трогается.

Пометки происхождения:

- **[запуск]** — воспроизведено запуском билдера (сгенерированный SQL, а для SQLite ещё и исполнение на живой базе в памяти);
- **[анализ]** — вывод из чтения кода и документации, живым сервером не проверено (MySQL/MariaDB/PostgreSQL/ClickHouse у меня нет).

## 1. Находки

### 1.1. Значение форматируется по содержимому, а не по PHP-типу

Корень: `is_numeric($value)` решает, ставить ли кавычки. Строка `'0123456789'` уходит в SQL числом.

- **[запуск] Запись.** `insertRow(['inn' => '0123456789', 'code' => '1e3'])` → `VALUES (0123456789, 1e3)`: в varchar пишется `123456789` и `1000`. То же в `updateRow`. Место: `AbstractSqlBuilder::formatValue` (строка 544), используется в INSERT/UPDATE, в ClickHouse и Oracle тоже.
- **[запуск] Условия.** `in('inn', ['0123456789'])` → `IN (0123456789)`, а `eq` на то же значение ставит кавычки. Место: `ConditionBuilder::in/notIn`.
- **[запуск] CALL.** `procedure('p', ['00123', '1e3'])` → `CALL p(00123, 1e3)`. Места: `buildProcedure` в Mysql, Pgsql, Mssql, Oracle.
- **[анализ] Upsert/merge.** Та же логика в `AbstractConflictBuilder::set`, `AbstractMergeBuilder`, `OracleMergeBuilder`, `PgsqlSqlBuilder` (строки 68, 104).
- **[запуск] bool на записи.** `insertRow(['active' => false])` → `''`, `true` → `'1'` (строкой). В строгом режиме MySQL это ошибка `Incorrect integer value`, в нестрогом — 0 с предупреждением. В условиях bool даёт `1/0` без кавычек, то есть два пути ведут себя по-разному.
- **[анализ] float.** `INF`/`NAN` превращаются в `INF`/`NAN` без кавычек, что читается как имя колонки.

Правило, которое предлагаю ввести везде: решает PHP-тип.

- `int`, `float` (конечный) → литерал без кавычек;
- `string` → всегда в кавычках, даже если выглядит числом;
- `bool` → литерал драйвера (для MySQL `1`/`0`);
- `null` → `NULL`;
- `INF`/`NAN` → исключение.

Последствие для вызывающего кода: числовые строки (например, из запроса) начнут уходить в кавычках. MySQL, PostgreSQL, SQLite, MSSQL и Oracle сравнивают `int_col = '5'` корректно, индекс используется. ClickHouse — **[анализ]**, нужна проверка у тебя (см. шаг 0).

### 1.2. `in` / `notIn` выбрасывают пустую строку

**[запуск]** `in('code', ['', 'A'])` → `IN ('A')`, `notIn('code', [''])` → `1 = 1`. Фильтр `'' !== $v` задуман для разбора строки `'a,,b'`, но применяется и к массиву.

### 1.3. Дубль `in/notIn` в `Condition` и `ConditionBuilder`

`ConditionBuilder` переопределяет `in/notIn` из базового `Condition` только ради приёма `null`: в базе тип `array<scalar>`. Копия разошлась с оригиналом: база форматирует через типовой `formatValue` (строки в кавычках), копия — через `is_numeric`. Баг с ИНН живёт именно в копии, а `ConditionJoin` использует базовую версию. Почему сделали копией, а не расширили базу, из истории не восстановить: в git один коммит «Initial release».

Поведение `NOT IN (..., NULL)` оставляем как есть, на усмотрение инженера. NULL просто передаётся в SQL.

### 1.4. LIKE: граница не ставится, а на части движков экранирование не работает вовсе

- **[запуск] Все драйверы.** `applyLikeBoundary` проверяет `%` по краям уже **после** экранирования. У `'50%'` экранированный хвост `\%` заканчивается на `%`, поэтому `like('name', '50%')` даёт `LIKE '50\\%'`: точное совпадение вместо «содержит». Для MSSQL баг не проявляется, потому что там хвост `[%]`.
- **Фикс уже был?** В этом репозитории истории нет. Тесты `testMysqlEscapeLikePattern`, `testPgsqlEscapeLikePattern`, `testSqliteEscapeLikePattern` с `LIKE_RIGHT` **закрепляют ошибочный вывод** (ожидают `'50\%'` без завершающего `%`). То есть тест подогнан под баг, а не баг починен.
- **[запуск] SQLite.** В SQLite у LIKE нет символа экранирования по умолчанию, нужен `ESCAPE '\'`. На живой базе `like('name', '50%', LIKE_RIGHT)` и `like('name', 'a_b')` вернули **ноль строк** при наличии `'50%'` и `'a_b'` в таблице. Любой поиск с `%` или `_` в значении не находит ничего.
- **[анализ] Oracle.** То же: без `ESCAPE` обратный слэш в LIKE не экранирует. Экранирование `[` в Oracle бессмысленно.
- **[анализ] PostgreSQL.** См. 1.6: экранирование LIKE ломается из-за удвоения обратного слэша в литерале.

### 1.5. Экранирование строк в MySQL и `NO_BACKSLASH_ESCAPES`

**[анализ]** `MysqlDriver::escapeValue` экранирует кавычку как `\'`. При `sql_mode` с `NO_BACKSLASH_ESCAPES` обратный слэш в литерале становится обычным символом, и значение `a\' OR 1=1 -- ` выходит из литерала: `'a\\\' OR 1=1 -- '` → строка `a\\\` закрывается, дальше идёт исполняемый `OR 1=1`.

Предлагаемый фикс: кавычку удваивать (`''`). Это работает в обоих режимах. Обратный слэш по-прежнему удваивать: в обычном режиме так и нужно, а при `NO_BACKSLASH_ESCAPES` это исказит данные (`\` → `\\`), но инъекции не даст. Полностью корректно при неизвестном режиме экранировать нельзя; это граница подхода «строка без соединения». Вариант на будущее — режим драйвера `noBackslashEscapes`, который задаёт инженер.

Перед правкой — проверка на живом сервере (шаг 0).

### 1.6. PostgreSQL: удвоение обратного слэша

**[анализ]** `PgsqlDriver::escapeValue` удваивает `\`. С `standard_conforming_strings = on` (умолчание с PG 9.1) обратный слэш в `'...'` — обычный символ, поэтому `C:\dir` запишется как `C:\\dir`. Инъекции нет (кавычка удваивается), есть порча данных и сломанный LIKE. Это та же граница класса, что и 1.5.

### 1.7. Компактор портит литералы

**[запуск]** `getQuery(true)`: `'O\'Neil  x'` → `'O\'Neil x'`. `SqlCompactor` знает только экранирование `''`. На `\'` он считает строку закрытой и схлопывает пробелы внутри значения. В INSERT/UPDATE это запись искажённых данных.

**[анализ]** Там же: однострочный комментарий `-- ...` в raw-выражении после схлопывания перевода строки закомментирует остаток запроса.

После перехода MySQL на `''` (1.5) литералы, которые генерирует сам билдер, компактор разбирает верно. Raw-выражения пользователя с `\'` (MySQL, ClickHouse) остаются, поэтому компактору нужен режим «обратный слэш экранирует», который задаёт драйвер.

### 1.8. `ON DUPLICATE KEY UPDATE ... VALUES(col)`

**[анализ]** В MySQL с 8.0.20 это deprecated (предупреждение 1287), замена — алиас строки: `INSERT ... VALUES (...) AS new ON DUPLICATE KEY UPDATE c = new.c` (с 8.0.19). В MariaDB алиаса нет, там только `VALUES()`. Удалён ли `VALUES()` в MySQL 9.x, я не проверял.

Билдер работает без соединения, поэтому версию сам узнать не может. Варианты:

- **A (рекомендую).** Необязательная строка версии сервера в драйвере, как `serverVersion` в Doctrine DBAL. Инженер берёт её из `PDO::ATTR_SERVER_VERSION`. `MariaDB` в строке → `VALUES()`; MySQL ≥ 8.0.19 → алиас; версия не задана → `VALUES()`, потому что работает везде, где работает сейчас.
- **B.** Явный флаг режима upsert у MySQL-драйвера (`valuesFunction` / `rowAlias`).
- **C.** Ничего не менять, пока `VALUES()` не удалят.

### 1.9. Литерал в SELECT не выразить

**[запуск]** `select('1')` → `InvalidQueryException`, а `select(Field::set('1'))` → `` SELECT `1` ``: число квотируется как идентификатор, и MySQL прочтёт его как имя колонки. Идиому `EXISTS (SELECT 1 ...)` собрать нельзя. В доках примеры переведены на `select('*')`. Решение: числовой литерал в `Field` не квотировать либо явный способ передать литерал.

### 1.10. Комментарии вне doc-блоков

`src/QbConsts.php`: 5 строчных комментариев-разделителей (строки 12, 22, 29, 34, 38). По правилу «комментарии только в doc-блоках» — удалить при первой правке файла.

## 3. Шаги

Каждый шаг заканчивается прогоном phpunit, phpstan и php-cs-fixer и точечной пробой из раздела «Проверка».

### Шаг 0. Проверки на твоей стороне (до правок)

Готовлю скрипт `build-dev/probe/escaping.php` (в `.gitignore`), DSN — из переменной окружения. Скрипт:

- в MySQL создаёт временную таблицу с одной строкой, выполняет собранный билдером запрос с `a\' OR 1=1 -- ` при обычном `sql_mode` и при `NO_BACKSLASH_ESCAPES` и печатает число строк. Ожидание **[анализ]**: 0 и 1;
- проверяет вариант с `''` в обоих режимах. Ожидание: 0 и 0;
- в PostgreSQL пишет и читает `C:\dir` и `50%` через LIKE;
- в ClickHouse (если есть) проверяет `UInt64_col IN ('5')`.

Результат отдаёшь сырым, план корректируется по нему.

### Шаг 1. Типовое форматирование значений (1.1)

- Единый метод форматирования значения по PHP-типу — на драйвере (`DriverInterface::formatValue` или рядом с `quoteValue`), чтобы bool-литерал и прочие особенности жили в одном месте.
- Перевести на него `AbstractSqlBuilder::formatValue`, `Condition::formatValue`, все `buildProcedure`, `AbstractConflictBuilder::set`, `AbstractMergeBuilder`, `OracleMergeBuilder`, `PgsqlSqlBuilder`.
- `INF`/`NAN` → `InvalidQueryException`.

Проверка: `insertRow`/`updateRow`/`in`/`procedure`/upsert с `'0123456789'`, `'1e3'`, `5`, `5.5`, `false`, `null` — строки в кавычках, числа без, bool как литерал драйвера. `grep is_numeric src` показывает только `SqlSecurity`.

### Шаг 2. Убрать дубль `in/notIn` (1.3, 1.2)

- Одна реализация в `Condition`, принимает `?scalar`, форматирует через метод шага 1. Override в `ConditionBuilder` удаляется.
- Фильтр пустых — по решению 2.2.

Проверка: `in` в WHERE, HAVING и JOIN даёт одинаковый SQL; `in('code', ['', 'A'])` → `IN ('', 'A')`.

### Шаг 3. LIKE (1.4)

- `applyLikeBoundary` применяет границу всегда, без проверки на `%`. Экранированное значение шаблоном быть не может, проверка там ошибочна по построению.
- Для драйверов, где у LIKE нет экранирования по умолчанию (SQLite, Oracle), генерировать `ESCAPE '\'`. Ставить ли `ESCAPE` явно и в MySQL/PG для однородности — решу по результату шага 0 и покажу.
- Исправить три теста, которые закрепляют баг.

Проверка: на живом SQLite `like('name', '50%', LIKE_RIGHT)` находит `'50%'` и `'5000'` не находит, `like('name', 'a_b')` находит `'a_b'` и не находит `'axb'`.

### Шаг 4. Экранирование MySQL (1.5)

Кавычка → `''`; `\`, `\0`, `\n`, `\r`, `\Z` — как сейчас. Только после шага 0.

Проверка: скрипт шага 0 — 0 строк в обоих режимах.

### Шаг 5. Компактор (1.7)

- Драйвер сообщает компактору, экранирует ли обратный слэш (MySQL, ClickHouse — да).
- `-- ...` до конца строки: перевод строки после комментария сохраняется.

Проверка: `'O\'Neil  x'` не меняется; raw-выражение с `-- комментарий\n` не съедает остаток запроса.

### Шаг 6. Upsert в MySQL (1.8)

По выбранному варианту. Для A: параметр версии, разбор MariaDB/MySQL, тесты на три ветки.

## 4. Вне плана

- Переход на bind-параметры — отдельная архитектурная тема.
